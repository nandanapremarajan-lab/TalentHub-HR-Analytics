# TalentHub Project Report
## 1. Introduction
TalentHub is an HR analytics database project that combines employee attrition analysis with a demonstration recruitment workflow. It is designed for the DBMS for Analytics course.

## 2. Objectives
- Design a relational HR database in Third Normal Form (3NF).
- Store departments, positions, candidates, applications, interviews, employees and exits.
- Analyse attrition by department, role, overtime, satisfaction and tenure.
- Demonstrate recruitment funnel and interview metrics.
- Connect Python to PostgreSQL using DB-API and visualize query results.
- Store flexible candidate résumé information in MongoDB.

## 3. Dataset
The employee/attrition sample is taken from the Kaggle IBM HR Analytics Employee Attrition & Performance dataset. The source contains 1,470 fictional employee records and 35 columns. This project selects the first 500 rows. The Kaggle dataset does not include recruitment applications, interview events, hire dates or exit dates. Therefore, candidate, application and interview records are synthetic demonstration data generated by the project. This distinction is maintained in the README and code.

## 4. Relational Design and Normalization
The PostgreSQL design contains:
1. `departments` — department master data.
2. `positions` — positions belonging to departments.
3. `candidates` — candidate profile and source channel.
4. `applications` — candidate applications for positions.
5. `interviews` — interview rounds and outcomes.
6. `employees` — employee attributes and attrition label from Kaggle.
7. `exits` — records employees whose Kaggle attrition label is Yes.
8. `application_stage_log` — trigger-generated application stage history.

Each entity has a primary key. Relationships use foreign keys. Repeating department and position details are stored once in their master tables. Applications reference candidates and positions; interviews reference applications; employees reference departments and positions; exits reference employees. This reduces duplication and supports 3NF.

## 5. Trigger and View
- Trigger `trg_application_stage_change` records old and new application stages in `application_stage_log`.
- View `vw_department_attrition` calculates employee headcount, leaver count and attrition percentage by department.

## 6. SQL Analysis
The SQL script includes queries for department and role attrition, overtime comparison, tenure bands, recruitment funnel, interview pass rates, positions with high application counts, above-department-average income, satisfaction comparison and employees with low satisfaction plus overtime.

## 7. Python DB-API and Visualization
The notebook uses `psycopg2` to connect to PostgreSQL and pandas to retrieve SQL query results. Matplotlib charts show attrition by department, overtime, tenure, and recruitment stage. Recruitment charts must be interpreted as synthetic demonstration output.

## 8. MongoDB
MongoDB stores flexible résumé documents with skills, education and experience arrays. The demonstration includes insert, find, update and delete operations; indexes on candidate ID and skills; and two aggregation pipelines for common skills and experience bands.

## 9. SQL vs NoSQL
| Relational SQL (PostgreSQL) | Document NoSQL (MongoDB) |
|---|---|
| Structured tables and relationships | Flexible JSON-like documents |
| Strong PK/FK constraints | Flexible nested résumé structure |
| Suitable for joins and consistent HR transactions | Suitable for variable résumé sections and skill arrays |
| SQL queries and views | CRUD, indexes and aggregation pipelines |

## 10. Limitations
The Kaggle dataset is fictional and has no date fields for hiring or exits. Recruitment records in this project are simulated. The project does not claim to measure real recruitment performance or predict individual employee behaviour. The results are for academic demonstration only.

## 11. Conclusion
TalentHub demonstrates a normalized relational HR database, analytical SQL, Python DB-API reporting and MongoDB résumé storage. It provides a practical example of using SQL for structured HR records and NoSQL for flexible candidate documents while clearly distinguishing sourced data from generated demonstration data.
